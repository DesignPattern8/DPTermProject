# [005] 셀 수 집계와 승패 판정

- 상태: 채택
- 작성자: Son2kwon / 2026-11-03 / 관련 이슈: #6
- 근거 명세: [rules.md](rules.md) 6장(종료 조건과 승패 판정)

## 문제

rules.md 6장의 판정 규칙은 세 가지다.

| 조건 | 검사 시점 | 결과 |
| --- | --- | --- |
| 한쪽 셀 수 = 0 | 시뮬레이션 중 매 세대 직후 | 즉시 종료, 남은 쪽 승 |
| 양쪽 셀 수 = 0 (같은 세대) | 위와 같음 | 즉시 종료, 무승부 |
| R번째 라운드의 시뮬레이션 완료 | 마지막 시뮬레이션 직후 | 셀 수가 많은 쪽 승, 같으면 무승부 |

#6 1차의 `SimulationPhase`는 K세대를 세기만 하고 셀 수를 보지 않는다(003 "이번 범위와 남은 것"). 두 가지를 정해야 한다.

1. **판정 로직을 어디에 둘 것인가.**
2. **셀 수를 어떻게 얻을 것인가.** 셀 상태 표현은 Cell 인터페이스 회의(#5) 전이라, 게임 진행 쪽에서는 보드에 셀 수를 묻는 방법만 정할 수 있다.

## 1. 판정 로직의 위치

### A. `SimulationPhase` 안에 직접 작성

`tick()` 안에서 셀 수를 읽어 조건문으로 판정한다.

- 장점: 새 타입이 없다. 판정이 세대 진행 바로 옆에 있다.
- 단점: 판정 규칙(숫자 두 개 → 결과)만 따로 테스트할 수 없고, 항상 게임을 시뮬레이션 단계까지 진행시켜야 확인할 수 있다. 세대 세기·단계 전환·판정이 한 메서드에 섞인다.

### B. 판정만 하는 별도 클래스 (패턴 없음)

```java
final class GameJudge {                                   // package-private
  static Optional<GameResult> afterGeneration(int a, int b);  // 전멸 검사
  static GameResult afterLastRound(int a, int b);             // R라운드 종료 판정
}
```

- 장점: 판정 규칙이 셀 수 두 개만 받는 순수 함수라, 보드나 게임 없이 숫자로 바로 확인할 수 있다. `SimulationPhase`는 "언제 판정하는가"만 맡는다.
- 단점: 타입이 2개(`GameJudge`, 결과 타입) 늘고, 판정 호출이 한 단계 생긴다.

### C. Strategy — `WinCondition` 인터페이스와 구현

B의 판정을 인터페이스로 만들어 게임에 주입한다.

- 장점: 판정 규칙을 실행 중에 바꿀 수 있다(예: 누적 점수, 영역 점수).
- 단점: rules.md 6장은 판정 규칙을 하나로 정했고, 다른 점수 방식은 **기각된 대안**이다("누적 점수나 영역(칸) 점수는 채택하지 않았다"). 바꿀 대상이 없는 인터페이스 1개와 주입 경로가 늘어난다.

### D. Observer — 판정자가 세대 진행 이벤트를 구독

- 장점: 시뮬레이션 단계가 판정자를 몰라도 된다.
- 단점: 판정 결과로 **단계를 바로 끝내야** 하는데(즉시 종료), 구독자가 게임 단계를 바꾸려면 다시 게임을 알아야 한다. 결과를 돌려받는 쪽이 자연스럽다(004에서 C를 기각한 이유와 같음).

## 2. 셀 수를 얻는 방법

게임 진행은 `TwoPlayerBoard`에 `int count(Player owner)`를 추가해 묻는다. 대역(`StubBoard`)은 테스트가 정한 셀 수를 돌려준다. **실제 보드가 셀 수를 어떻게 셀지**는 셀 상태 표현이 정해지는 #5에서 정한다. 그때 비교할 후보만 적어 둔다.

| 후보 | 내용 | 메모 |
| --- | --- | --- |
| 보드 전체 순회 | `count` 호출마다 64×64 = 4,096칸을 센다 | 세대마다 판정 1번 + 상태 표시 1번 정도라 비용이 작을 것으로 추정 |
| 증분 집계 | 놓기·세대 전이 때 셀 수를 갱신해 둔다 | `count`는 O(1). 대신 `Resident.transition()`과 `Neighborhood` 쪽에 갱신 지점이 생긴다 |
| Visitor (`CountingVisitor`) | rules.md 8장의 후보. 셀 트리를 방문하며 상태별로 센다 | `Cell`에 `accept`가 필요해서 #5 회의 안건(001 후보 D)과 같이 정해야 한다 |

## 결정과 근거

**B(패턴 없이 판정만 하는 별도 클래스)를 채택한다.**

- 판정 규칙은 "셀 수 두 개 → 결과"인 순수 함수다. 별도 클래스로 두면 rules.md 6장 표를 그대로 숫자 테스트로 옮길 수 있고, `SimulationPhase`는 "매 세대 직후 / 마지막 세대 직후에 판정한다"는 시점만 책임진다.
- C(Strategy)는 바꿀 판정 규칙이 없다. 다른 점수 방식은 rules.md에서 기각됐다. 규칙을 바꿔야 할 일이 생기면 `GameJudge`의 두 메서드를 인터페이스로 빼면 되고, 호출하는 곳은 `SimulationPhase` 한 곳뿐이다.
- A는 타입이 가장 적지만, 판정을 확인하려면 항상 게임을 시뮬레이션까지 진행시켜야 한다.
- D는 즉시 종료를 위해 구독자가 게임 단계를 다시 바꿔야 해서 맞지 않는다.

### 정한 세부 규칙

- 전멸 검사는 **매 세대 직후** 한다. K번째 세대에 전멸하면 개입으로 넘어가지 않고 그 자리에서 종료한다(마지막 라운드가 아니어도). 마지막 라운드의 K번째 세대에 전멸이면 셀 수 비교가 아니라 전멸로 판정한다.
- 배치·개입 단계에서는 판정하지 않는다(rules.md 6장).
- 점수(상태 표시용)는 현재 보드의 자기 셀 수다. `TwoPlayerGame.score(player)`는 `board.count(player)`를 그대로 돌려준다.
