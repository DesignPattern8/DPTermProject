# 측정: `Resident.transition()` 반환값 수정 전후의 재계산 블록 수

- 관련 이슈: #12
- 측정일 / 측정자: 2026-11-03 / Son2kwon
- 관련 테스트: `ClassicCellTest#onlyBlocksNearChangesAreRecomputed` (CL-C-08)

## 무엇을 쟀나

tick 한 번에 **셀을 다시 계산한 `Neighborhood` 수**. `Neighborhood.figureNextState()`는 자기가 활성이거나 이웃 블록이 자기 쪽 가장자리를 활성으로 표시했을 때만 안쪽 셀을 다시 계산한다(`Neighborhood.java:121-129`). 그 분기에 들어간 횟수를 센다.

- 보드: `Universe`와 같은 구성. 바깥 `Neighborhood` 1개 안에 8×8 하위 `Neighborhood` 64개, 각각 8×8 `Resident` (64×64칸).
- 수치에는 **바깥 블록 1개가 포함**된다. 따라서 최대값은 65(하위 64 + 바깥 1)이고, 하위 블록 수는 표의 값 − 1이다(바깥 블록이 활성일 때).
- tick은 `Universe`의 Clock 리스너와 같은 순서(`figureNextState` → true면 `transition`)로 돌렸다.

## 방법

- 계측: `Neighborhood`에 package-private 정적 카운터 `recomputedNeighborhoods`를 두고, 위 분기에 들어갈 때마다 1 증가. 테스트 계측 전용이며 public API는 바뀌지 않았다.
- 측정 프로그램: 같은 패키지(`com.holub.life`)의 별도 프로그램이 tick마다 카운터를 0으로 되돌리고 tick 후 값을 읽는다. 저장소에는 커밋하지 않았다.
- 수정 전: 카운터만 들어간 커밋(`db637eb`)의 빌드. 수정 후: 수정 커밋(`94cdaa6`)의 빌드. 같은 측정 프로그램을 두 빌드에 돌렸다.
- 환경: JDK 26.0.2.1, Apple M4 Pro, macOS, headless, `-ea`

## 해석

- 수정 전에는 움직이는 것이 있으면 tick 2부터 65(전체)를 다시 계산했다. 하위 블록의 가장자리 셀 중 **안 바뀐** 셀이 하나라도 있으면 그 방향이 활성으로 표시됐기 때문이다(`Neighborhood.java:240`에서 뒤집힌 반환값을 사용. 수정 전 줄 번호는 232).
- 수정 후에는 실제로 바뀐 블록과 그 이웃만 다시 계산한다. glider는 평균 64.7 → 3.3, blinker는 63.8 → 4.0.
- 무작위 보드는 처음에 거의 모든 블록이 움직여서 앞쪽 tick은 수정 후에도 65다. 보드가 가라앉으면서 차이가 난다(평균 65.0 → 50.6~55.7).
- 정물(block)만 있으면 수정 전후 모두 tick 2부터 0이다. 이때는 `figureNextState()`가 false라 `transition()`이 호출되지 않는다.
- 보드 결과는 같다: 세대 진행 특성 테스트 CL-G-01~10(그중 CL-G-07~10은 단순 구현 `ReferenceLife`와 매 세대 비교)이 수정 전후 모두 통과했다.

## CL-C-08의 기준값

CL-C-08은 glider 보드에서 tick 2~10의 값이 **5 이하**인지 확인한다. 수정 후 이 구간의 실측값은 매 tick 2이고, 240 tick 전체의 최대값이 5다. 수정 전에는 tick 2에서 65가 나와 실패한다.
